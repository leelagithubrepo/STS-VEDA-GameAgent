VEDA — AI Advisor for Turn-Based Games

What if a game advisor could learn with you?

VEDA watches the game, understands the situation, recommends what the player should do, predicts what may happen, checks what actually happened, and learns from the experience. The player always remains in control.

01

What VEDA does

A game adapter provides observation and legal actions. VEDA preserves verified state, assesses the threat, compares options, forecasts a result, and records what actually happened. An LLM can mentor the system at defined review points; the player decides what to execute.

State

Facts stay separate from guesses

HP, Energy, hand, enemies, intent, deck, relics, potions, gold, and route are recorded only when supported by the current screen or a named source.

Decision

Forecast before recommendation

VEDA records the chosen line, alternatives, confidence, and checkable predictions. Unknowns remain visible instead of being filled with memory.

Learning

Outcome earns the lesson

Experience does not silently become policy. A proposed lesson needs evidence, a specific implementation, and a regression test before it changes strategy.

03

How VEDA evolves

The architecture is deliberately designed to move from LLM-assisted construction toward independent, evidence-based improvement without hiding uncertainty.

Phase 1

LLM builds VEDA

Architecture, perception, rules, safety checks, knowledge stores, decision protocol, and telemetry are designed and tested.

Phase 2

VEDA runs standalone

VEDA observes, reasons, advises, and records locally. The player retains controller authority.

Phase 3

LLM review loop

At handoff points VEDA submits evidence, decisions, uncertainty, and outcomes for a targeted external review.

Phase 4

Experience improves policy

Retrospection becomes a controlled loop: outcome → evaluation → tested lesson → knowledge update → better future advice.

Private review protocol, shown as a message shape—not a published conversation:
VEDA → reviewer: prediction differed from outcome; evidence and uncertainty attached.
reviewer → VEDA: add the missing state to the threat calculation; validate it before promotion.

The public Report Card exposes outcomes and evidence, never the private conversation.

04

Memory and communication

VEDA’s empirical memory connects observation, decision, outcome, and retrospective. The standalone inbox creates an explicit handoff: a separate terminal session has not “received” a review until it reads and acknowledges it.

Local history

Portable evidence store

Current local records are file-backed and structured for later database migration. The data model preserves provenance, timestamps, state, prediction, result, and review status.

Review boundary

Mentored, not remote-controlled

The reviewer helps diagnose blind spots and recommends validation work. VEDA owns local records and only changes strategy after the evidence gate is satisfied.

Future games

Adapter, not redesign

Slay the Spire is implementation one. A second turn-based game should supply its own observation and rules adapter while reusing VEDA’s reasoning, telemetry, and learning loop.

05

Telemetry is the proof of improvement

VEDA uses telemetry as evidence—not as decoration. Metrics are published only when the underlying record is present.

System

Perception confidence, latency, model timing, capture health, and failures.

Decision

Recommendation, alternatives considered, confidence, explicit forecast, and uncertainty.

Game

Act, floor, HP, Energy, enemies, deck, relics, potions, gold, and route.

Outcome

Predicted versus actual damage, battle result, rewards, losses, and resource changes.

Learning

Retrospectives, proposed and validated lessons, recurring mistakes, and calibration trend.

Public view

The report exposes concise game evidence while keeping private reviewer exchanges private.
